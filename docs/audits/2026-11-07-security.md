- `admin_login` : search_path vide, références aux objets applicatifs qualifiées ; signature et comportement conservés.
- `access_login` : nouvelles sessions de 30 jours (au lieu de 180). Les sessions déjà émises gardent leur expiration ; pas de déconnexion générale. Le renouvellement reste une nouvelle connexion, sans rotation transparente ajoutée.
- Documents : nouveaux envois en attente ; les documents et parcours existants restent approuvés. Lectures publiques filtrées côté serveur, y compris lecture directe par UUID. Nouveau parcours masqué jusqu'à approbation.

- RLS activée uniquement pour les deux tables communautaires touchées, en complément des ACL privées ; aucune politique publique, aucun changement global aux 19 autres tables.
- Déploiement Pages conditionné au succès de la suite complète sur Postgres 17, y compris les nouveaux tests.

## Tests et limites

- Tests ciblés du cycle de jeu, accès et modération sur PostgreSQL embarqué PGlite : premier passage 16/16.
- Tests de modération : validation, URL interdite, confidentialité de l'attente, répétition idempotente, jeton invalide, approbation, refus d'une deuxième revue, rejet, confidentialité du nouveau parcours, quota horaire, réinstallation.
- Tests auth supplémentaires : session existante conservée et nouvelle session bornée à 30 jours.
- `npm run test:pglite` rend la vérification locale reproductible. Le scénario de 48 connexions utilise un Pool TCP Postgres et est exclu de ce mode embarqué seulement ; il reste dans la CI Postgres native. PGlite ne prouve pas le comportement concurrent multiconnexion.
- Une limite par origine fiable n'est **pas** implémentée : les appels SQL anonymes n'offrent pas ici une identité d'origine de confiance. Les plafonds globaux restent saturables par un attaquant ; la modération empêche la publication automatique mais ne remplace pas un service de confiance/CAPTCHA ou une authentification. #77 reste ouvert pour ce point.
- Les sessions d'accès reposent toujours sur le numéro autorisé ; réduire leur durée n'ajoute pas une preuve d'identité. L'audit complet des abus de chaque RPC et une politique de rotation restent à poursuivre dans #76.

## Retour arrière

Les migrations n'effacent aucune donnée de jeu. Les définitions antérieures sont conservées. Pour restaurer une fonction, exécuter uniquement sa définition sauvegardée, en conservant ses ACL. Pour revenir sur la modération, **ne pas** restaurer les lectures non filtrées tant que des contributions en attente/rejetées existent : cela les publierait. Préférer conserver le filtrage et corriger le flux. Les colonnes ajoutées sont additives et ne doivent pas être supprimées pour un retour arrière du frontend.
